# 汇报稿：把一篇导读整理成一张可以讲的导图

汇报稿是导读之上的一层可选内容，给组会这类场合用：听的人没读过论文，讲的人只有十分钟出头，要简洁讲清整篇论文的价值。它把论文整理成一张导图——中心是论文，三四条分支是汇报的几个部分，每条分支上是两三个讲解点，讲解点下挂着关键词。每个讲解点再配一句要记住的话、原图或表和出处。组会是共享屏幕，听的人看得到整页，所以页面上只放展示材料；讲稿提示留在汇报稿文件里，供讲者准备时看，页面和打印讲义都不显示。导读正文不动，汇报稿也不能替代它。

一份汇报稿对应一个导读修订，文件是 `content/presentations/<guideId>.r<revision>.json`。修订升级后，旧汇报稿仍然只属于旧修订；需要时为新修订另写一份。

## 页面怎样使用它

- **全图**（`/present/<guideId>/<revision>` 顶部）：一句话主张、完整的导图（每个分支、讲解点和关键词）和一行汇报顺序，让听的人先知道要讲什么。鼠标指向一个分支时，这一支亮起、其他分支变淡；点导图上的任何分支或讲解点，下面的讲解跳到那里。页面只在标题下写总时长，各节不标时间；计划时间留在汇报稿里，供试讲时对照。
- **跟着讲的导图**（往下滚动）：左侧导图固定在屏幕里，右侧按导图顺序排出每个讲解点的内容——一句结论、原图或表、关键词说明、出处和“导读原文”。开场时左侧只画主干；滚到一个分支，导图展开这一支、收起其他分支并框住它；滚到一个讲解点，它和通往它的连线被点亮、关键词从它旁边长出来；到收束时全部分支展开。地址 `#<stopId>` 直接打开到这一点。
- **打印讲义**：全图一页，之后每个分支另起一页。

入口在书架信息卡的“组会汇报”和阅读页工具栏的“汇报”，只有存在汇报稿的修订才显示。

## 文件格式

```json
{
  "schemaVersion": 1,
  "guideId": "multi-agent-communication-survey",
  "revision": 2,
  "title": "汇报标题",
  "minutes": 12,
  "thesis": "一句话说清这篇文章的主张。",
  "review": "依据哪一版导读整理，谁核对过，没有核对什么。",
  "opening": { "minutes": 0.75, "message": "开场要说的一句话", "notes": ["…"] },
  "parts": [
    { "id": "system", "title": "系统层", "summary": "这一部分讲什么，一句话。", "stops": [ { "…": "…" } ] }
  ],
  "closing": { "title": "收束标题", "minutes": 1.25, "message": "…", "points": [ { "key": "…", "text": "…" } ], "notes": ["…"] }
}
```

每个讲解点（`stops` 中的一项）：

| 字段 | 说明 |
|---|---|
| `id` | 小写字母、数字和连字符；全稿唯一，也是这一点的地址 `#id`。`opening`、`closing` 保留。 |
| `title`、`label` | 内容标题（不超过 40 字）；`label` 是导图上的短名（不超过 14 字）。 |
| `minutes` | 计划讲多久，以 0.25 分钟为单位。开场、全部讲解点和收束相加必须等于 `minutes`。 |
| `unitId` | 对应的导读章节，用于“导读原文”。 |
| `message` | 这一点要让听众记住的一句话（不超过 120 字）。 |
| `points` | 最多 6 条。`key` 是关键词，讲到这一点时出现在导图上；`text` 是一句说明（不超过 130 字），放在讲稿里；没有图和表的讲解点，卡片上也显示要点。 |
| `figure` | `asset` 必须是这个导读修订已声明的原图；`caption` 写怎样读这张图。 |
| `table` | 2–6 列、最多 8 行；`note` 写数字来源或读表时要留意的条件。 |
| `notes` | 讲稿提示，1–4 条。只在文件里，供讲者准备；页面和打印讲义都不显示。 |
| `sources` | 出处。链接必须是这个导读修订已有的引用。 |

每个讲解点至少要有要点、原图或表格之一。部分为 2–6 个，每部分 1–6 个讲解点，全稿不超过 20 个。这些由 `server/content/presentations.mjs` 检查，`npm run validate:content` 会一并运行。检查只管结构：章节、原图和出处是否属于这一版导读，时间是否相加正确，文字是否短到能放进导图和一屏。**它不检查内容对不对。**

## 写的时候

1. **先画导图，再写内容。** 10–15 分钟大约 3–4 个部分、6–8 个讲解点，收束讲论文的价值与边界。部分应当是听众能复述的结构（例如“系统层 / 系统内部”），而不是“背景 / 方法 / 实验”这类万能标题；次要的维度可以只在一张总表里带过。
2. **一个讲解点只讲一件事。** `message` 写结论，要点写支撑它的两到五条；关键词要短到能在导图上读出来。
3. **只用导读里已有的内容。** 数字、条件、代表工作、出处都从导读修订中取，保留“谁清点的”“在什么条件下”这类限定。导读自编的教学例子要标明是教学设定；导读自己的整理要和论文作者的主张分开写。
4. **原图优先。** 综述的框架图、方法的结构图比文字要点更适合讲；图注写怎样读图，不重复图里的字。
5. **页面上的文字是给听的人看的。** 结论、要点和分支说明不写“讲到这里”“练习”“只带过”这类对讲者的话；过渡、读图顺序、时间紧时略过什么写进 `notes`。
6. **留给讨论的问题要标明来源。** 它是整理者准备的提问，不是论文结论，也不是读者本人的判断。

写完运行 `npm run validate:content`，再打开汇报页：先看顶部导图每个标签是否读得清，再往下滚动逐点走一遍，确认左侧导图跟着换到对应分支，并按计划时间试讲一次。`review` 字段如实写明核对到什么程度。
