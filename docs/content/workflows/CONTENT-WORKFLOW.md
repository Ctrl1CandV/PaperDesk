# PaperDesk 内容生产与更新工作流

## 文档性质与目标

本文是制作、压缩、审阅和更新 PaperDesk 内容的长期工作流。它起源于提交 `1668527a9e84cacac85019c569f44719bb90252d` 的升级建议，相关工程任务已归入[历史材料](../../history/reading-ai-upgrade/README.md)。继续制作内容时，以[当前内容契约](../CONTENT.md)和[项目状态](../../development/PROJECT-STATE.md)为准；本文不依赖安装、修改或集成任何 skill、plugin，也不表示每篇材料已经完成全部核验。

目标是延续现有“书架筛选—导读决策—深读理解—有据问答”的阅读过程。保留目前完整自然段、连续论证和直接可见章节的展示方式。优化重点是稳定生产质量、保存解释所需条件，以及让每次修订都有明确来源。不要为增加字段而重做前端，也不要把自然段统一改成碎句、折叠面板或填空式卡片。

## 一、阶段、产物与完成标准

每篇材料须经过以下流程。某一步材料不足时，缩小交付范围并说明缺口；不得凭后续写作掩盖前面没有取得的证据。人可读审查记录放在项目内容研究文档中；长期原文材料与机器可读核验关系按02/03持久保存，制作过程的临时文件另放忽略目录，不能把唯一原文或人工核验结果当缓存清理。

| 阶段 | 输入 | 要求执行的动作 | 产物 | 完成标准 |
|---|---|---|---|---|
| 选文 | 学习问题、现有书架 | 说明该文补充什么、为何优先 | 选文理由与预期范围 | 能回答读完后应多理解什么 |
| 固定来源 | 论文与发表记录 | 区分学术身份、技术版本、发表信息 | 固定来源记录 | 正文、数字和图表来自明确版本 |
| 获取材料 | 固定来源 | 实际取得正文、附录和必要图表，登记失败项 | 获取与覆盖清单 | 已读、未读、未能取得可区分 |
| 分型提取 | 已取得原文 | 按文章类型提取主张、机制、证据和条件 | 提取稿及主张核对表 | 关键解释均能回到原文 |
| 连贯讲解 | 提取稿 | 完成深读初稿和导读，交叉检查 | Markdown 与 orientation 草稿 | 两层承担不同阅读任务 |
| 图表核查 | 相关论证与原图 | 核对图表，必要时制作教学图 | 图表记录、经审阅的展示材料 | 图文一致且作用清楚 |
| 压缩复核 | 原文与两层草稿 | 检查删减是否改变结论 | 缺口、修订与复核记录 | 条件、反例和归属没有丢失 |
| 独立审阅 | 完整候选内容包 | 从原文重新核对关键内容 | 内容审查结论 | 阻断问题解决或如实降范围 |
| 本地更新 | 已审内容包 | 校验、预览、导入新修订 | 新 revision 与导入记录 | 旧修订、个人记录保持可用 |
| 发布后核对 | 实际渲染结果 | 核查显示、引用和问答材料关联 | 验收记录 | 满足 [05 验收要求](../../history/reading-ai-upgrade/05-ACCEPTANCE.md) |

## 二、先选定阅读问题，再固定原文

选文理由应与具体理解缺口相连，例如“理解有限缓存为何仍能持续处理输入”，比“这是一篇高引用重要论文”更有用。已有材料能解决问题时，优先补充关联阅读入口；新增论文应说明它提供了什么不同机制或证据。推荐顺序属于编辑判断，应与论文证明的技术依赖分开，不根据平台内容推断读者已经掌握某项知识。

来源记录至少应明确论文身份、采用版本、来源 URL、取得日期、实际阅读章节和必要图表。arXiv 版本与正式发表版本可能存在作者、实验、页码差异；发表记录可以用于核验会议和年份，但不能把另一版实验数字直接混入正文。未知版本或日期应如实保留未知状态，不能用网页访问日期替代论文版本日期。

取得摘要、解析文本和看过图像是不同事实。公式、跨栏表格或图片信息参与论证时，要求打开对应页面核对，不能只依赖抽取文字和图注。材料缺失应说明它影响什么问题，而非只写“解析不完整”。仅有摘要时，应交付摘要依据的快速导读，使用相符的 `coverage.scope`、`coverage.basis` 和 `mode`；不得标为 deep，或补写看似完整的方法与实验。

## 三、按论文类型提取，保留研究的逻辑

提取稿用于保存事实和推理依赖，不要求直接显示给读者。使用现有 `type` 字段描述文章主类型；混合论文可以补充其他类型的检查项目，不必强行归为单一写作模板。

| 类型 | 必须提取的主要内容 | 最容易被压缩掉的部分 |
|---|---|---|
| 综述 survey | 讨论对象、范围、分类依据、类别关系、代表工作、评价和争议 | 分类并非互斥；分支间的联系；作者的时间边界 |
| 方法 method | 问题、输入输出、机制、训练与推理过程、对照和消融 | 哪个组件真正改变；额外数据、预算和先验条件 |
| 评测 evaluation | 测量对象、样本、协议、适配、指标和不确定性 | 数据污染、评分者影响、聚合口径与可比较性 |
| 理论 theory | 问题定义、假设、命题、证明关键步骤、结论范围 | 充分与必要、上界与实际表现、假设失效情形 |
| 系统 system | 架构、状态与数据流、组件职责、故障处理、成本 | 并发和负载条件、端到端指标、瓶颈及失败恢复 |

每个核心主张应记录原文位置、支持材料、成立条件、必要反例和归属。正文中的“作者提出”“实验观察到”“由此可推得”分别对应主张、证据和编辑解释；自然地交代即可，无需每句插入标签。教学例子可以帮助理解，但必须让读者知道它没有作为论文实验运行。

数字核对要求同时检查数据集与划分、模型、基线、指标方向、单位、样本量及计算预算；适用时还要保留重复次数、方差或置信区间。相对提升与百分点变化不可混写，开发集消融与测试集成绩不可并列成统一排名。系统比较同时改变多个组件时，不得把全部收益归因于单个机制。理论推导也应核对符号和假设，不能用一个教学例子代替证明。

## 四、导读与深读分别解决什么问题

导读帮助读者决定是否进入、准备什么以及从哪里开始。要求保留现有三段式表达：概述交代研究问题和主要贡献；阅读价值说明它能帮助分析什么；阅读建议把先修、顺序和关键边界连接起来。三段应各有信息，避免反复改写摘要或只说“具有重要意义”。字数依信息需要调整，不以固定句数或压缩比例决定质量。

深读应解释作者如何从问题走到方法，再走到证据。先讲清对象和必要概念，让公式、实验和例子在需要它们的位置出现。方法论文应让读者能够沿输入、状态变化和输出复述机制；综述应让读者理解分类为什么成立、分支怎样联系、不同证据能支持什么。保留长段落之间的因果与转折，不能把原文目录逐项换成一句总结。

`orientation.readingTargets` 与 `related` 会直接显示给读者：信息卡在对应章节下显示目标的 `purpose`，深读页在当前章节目录项下显示“本节要弄清”（`purpose`）与“留意”（`limit`）；`related` 显示为信息卡与文末的“相关导读”。因此每条目标应绑定到实际讲解它的单元，用一两句能独立读懂的话写清“读完能分辨或解释什么”，限制写清结论不能推广到哪里；不要写成摘要的复述或答案。深读页“读这类论文时可以留意”的问题由第三节的类型表压缩而来（`src/reader/reading-lens.ts`），修改该表时一并检查。

可先用简短导读草稿确定阅读方向，但最终导读必须依据已完成并复核的深读与提取稿回查；不能依靠另一份摘要反复压缩。`orientation` 承担可复用的导学信息，正文承担完整解释，二者不需要重复所有细节。概念关系复杂、状态变化多步或公式依赖难以用文字追踪时，应按 [02 来源与图示规范](SOURCES-AND-VISUALS.md)补图或安排专题深读，必要机制仍须有文字说明。

## 五、证据、图表与覆盖范围

关键结论旁应有可用的原文入口。要求核查链接指向的实际版本、章节、图表和物理页码；能够验证的锚点应尽量精确，不能定位的来源保留清楚的手动定位说明。HTTP 请求成功只能说明页面可访问，不能证明某个表格就在声明的位置，更不能证明它支持当前结论。

图表核查须包含坐标、图例、单位、分组、误差表示和图注中的条件。原图复用、重绘与原创教学图分别注明来源和性质；展示资产沿用项目已有的声明、校验和渲染边界，不新增图像生成服务依赖。正文依赖某幅图的细节而该图未核查时，应先核图、删去未经支持的细节，或降低覆盖声明。具体规则见 02。

`mode` 表达讲解深度，`coverage.scope` 表达覆盖广度。mainline 可以对关键机制讲得很深，同时明确未覆盖的附录和分支。full-survey 要求实质解释全部主要分支、必要证据与图表，完成所需来源核查；非重点分支也不能只列名称。长篇幅、齐全目录和 deep 标签均不能代替这些条件。

界面只需轻量提示采用版本与覆盖级别。对理解有直接影响的缺口应就近说明，例如讨论某图时注明只核到图注；完整清单留在覆盖说明和审查记录中。不得把所有限制都藏在文章末尾，也不要用大块元数据打断阅读。后续问答应使用同一覆盖信息，相关实施要求见 [03 AI 数据方案](../../history/reading-ai-upgrade/03-AI-DATA-IMPLEMENTATION.md)。

## 六、怎样检查压缩是否保真

每次压缩后，要求用研究问题检验文本：读者是否仍能解释机制为何有用、结果在什么条件下成立、有哪些失败情形，以及下一步该核原文哪里。能够回答这些问题比达到某个字数更重要。删除重复表述通常可行；删除假设、比较条件、反面结果或关键中间步骤，往往会改变结论。

检查时应把原文、提取稿、深读和导读并列，特别关注“可能”变为“能够”、“这一设置”变为“普遍”、“相关”变为“导致”等强度变化。还要检查分类关系是否被写成互斥类别、多个结果是否被合成一个并不存在的结论、历史挑战是否被当成当前研究空白。无法简写且仍然准确的内容应保留足够篇幅，或拆成有明确入口的专题；不能用“详见原文”替代当前讲解必需的一步。

## 七、独立审阅与两类真实样例

要求保留已有的逐主张审查方式。独立审阅者应从固定原文核对关键结论和条件，记录自己实际读过的部分及尚未核查的内容；只看作者自审报告或运行结构测试不算完成内容审阅。审阅结论至少区分：可以按声明范围发布、需修订、只能缩小范围、来源不足。数字与来源不符、关键机制缺失、把推演写成实验证据等问题应先解决。

**StreamingLLM 示例。** 基准正文保留了 Llama-2-13B、PG19 首书约 65K token、总缓存 1024 等条件，再给出纯滑窗困惑度 5158.07、保留四个初始 token 后 5.40、换行符替换后 5.60。它还解释累计处理长度与有效上下文的区别。后续压缩要求保留这些条件与区分，不能只留下“保留四个 token 就能无限记忆”。依据：[基准正文](https://github.com/Ctrl1CandV/PaperDesk/blob/1668527a9e84cacac85019c569f44719bb90252d/content/guides/streamingllm.md#L35-L63)、[核查记录](https://github.com/Ctrl1CandV/PaperDesk/blob/1668527a9e84cacac85019c569f44719bb90252d/docs/research/streamingllm-review.md#L17-L44)。

**Agent 记忆综述示例。** 基准正文把来源、形式、操作解释为交叉维度，并分开答案正确性、参考记忆检索和完整任务表现。它明确图3–5只核图注与页码，覆盖为 mainline。后续若要加入图像细节或提升覆盖等级，要求先完成相应原图与分支审阅，再发布新修订；不能仅改 `figuresViewed` 或 scope。依据：[分类与评价](https://github.com/Ctrl1CandV/PaperDesk/blob/1668527a9e84cacac85019c569f44719bb90252d/content/guides/agent-memory-survey.md#L25-L77)、[覆盖声明](https://github.com/Ctrl1CandV/PaperDesk/blob/1668527a9e84cacac85019c569f44719bb90252d/content/guides/agent-memory-survey.md#L87-L93)。

## 八、内容包、稳定标识与本地更新

要求继续使用 `guide-v2.schema.json`、JSON 元数据与 Markdown 正文，不向现有 schema 填入未经实现的额外字段。提取稿和审查表先作为研究记录保存；03 中拟议的证据结构须待相应实现和验收后使用。生成过程不得写入读者已读状态、私人笔记或个人判断。

`(id, revision)` 是不可变内容身份。修改正文、来源定位、覆盖声明、元数据或资产均应增加 revision，保留旧文件和旧路由；同一 guide ID 保持论文身份一致。原文发布新版时，应先审查差异和实际采用内容，再生成明确采用新来源的导读修订，不能原位替换旧版本依据。

`units` 必须与导言和二级标题的实际顺序对应。同一阅读单元延续到新修订时应尽量保留 ID；拆分、合并或改变语义时使用明确的新 ID，并记录旧目标的处理方式。不能仅因重新排序就给所有章节重编号，也不能把旧 ID 改指另一段论证。精确笔记与证据继续指向原修订，迁移规则另按 03 与 [04 实施任务](../../history/reading-ai-upgrade/04-CODEX-TASKS.md)执行。

`library-briefs.json` 是单独维护的展示文案，按 `guideId + guideRevision` 绑定。要求依据对应修订审阅概述、价值、建议、短章节名和来源日期。现导入器不接收该文件；应在应用侧单独编辑并预览，新修订没有匹配 brief 时沿用现有 orientation 回退逻辑，不能把旧 brief 套在新内容上。[基准更新合同](https://github.com/Ctrl1CandV/PaperDesk/blob/1668527a9e84cacac85019c569f44719bb90252d/docs/CONTENT-UPDATES.md#L5-L21)规定了这些边界。

本地候选包应包含完整预期目录及所有保留修订，更新正文哈希、引用库存和 current 指针后先执行：

```text
npm run import:content -- --from incoming/reviewed-release --dry-run
```

核对候选差异和内容审查结果后，在已授权范围内执行 `--apply`，再运行 `npm run validate:content` 与 `npm run build`，预览受影响的导读、正文、图表及来源返回行为。导入应沿用现有暂存、校验和原子切换路径，不手工覆写旧修订。这里的发布指本地内容更新，远端提交与部署仍按项目既有授权范围执行。

最终记录应分别说明结构检查、内容审阅、实际界面检查和仍未验证的部分。通过 schema、构建或引用数量检查，只能证明对应机械条件成立；不得据此宣布内容准确、讲解优秀或问答可靠。
