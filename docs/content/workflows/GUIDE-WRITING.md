# 导读写作工作流：从原文到可读的深读导读

本文是修订或新写一篇 PaperDesk 导读的完整工作流。它总结了 Transformer r5 和 RAG 综述 r5 两篇样例的写法，读者已确认这两篇达到要求。来源核对、证据与覆盖声明的规则仍以[内容生产工作流](CONTENT-WORKFLOW.md)和[来源与图示规范](SOURCES-AND-VISUALS.md)为准；“怎样写、写多长、写成什么样”，以本文为准。

**动手前，先完整读两篇样例：**

- 方法论文：`content/guides/transformer.r5.md`
- 综述：`content/guides/rag-survey.r5.md`

再读它们的信息卡，即 `content/library-briefs.json` 中这两篇第 5 版的条目。本文所有要求都能在样例里找到对应的写法；拿不准时，以样例为准。

## 一、读者是谁，导读要做到什么

读者是刚开始做研究的研究生：有基本的数学和编程背景，但很多领域术语和缩写没见过，读英文论文吃力，也还不熟悉“怎样读一篇论文”。导读要做到两件事：

1. **让读者真正读懂这篇论文。** 读懂它要解决什么问题、核心方法怎样一步步工作、证据支持了什么。读者读完应该能对着原论文的关键图，给别人讲清楚。
2. **保留读论文时的思考。** 读者要能看到作者的推理过程：作者注意到什么问题，为什么这样设计，用什么实验检验。导读不是摘要，也不是知识点清单。

以前的导读压缩过度：信息卡只有一百多字，正文每段结尾都有防误读的免责句，读起来像机械罗列。**现在不设字数上限。** 一篇导读通常在 15000–25000 字之间，篇幅首先给核心内容。

## 二、交付物与文件位置

修订一篇导读时，新建一个修订号 N（取该导读已有最大修订号加 1，可在 `content/catalog.json` 中查到）。旧修订不改动，也不删除。

为了让多篇导读可以同时修订，共享文件 `content/catalog.json`、`content/library-briefs.json`、`content/glossary.json` 由整合者统一合并，作者不要直接改。作者只写下面这些文件：

| 文件 | 内容 |
| --- | --- |
| `content/guides/<id>.r<N>.md` | 导读正文 |
| `content/guides/<id>.r<N>.json` | 元数据，由脚本生成，不手写 |
| `content/guides/assets/<id>/*.webp` | 原论文图（如果用到） |
| `.cache/guide-work/<id>/spec.json` | 生成元数据用的说明文件，格式见第九节 |
| `.cache/guide-work/<id>/brief.json` | 新修订的信息卡，格式见第六节 |
| `.cache/guide-work/<id>/glossary.json` | 需要新增的术语，格式见第七节；没有新增就写 `{"entries": []}` |
| `docs/research/<id>-r<N>-review.md` | 核对记录，格式见第十节 |
| `.source-review/<id>/` | 下载的原文和截图，不提交到 Git |

## 三、工作步骤

### 第 0 步：读现有材料

1. 读两篇样例导读和它们的信息卡。
2. 读这篇导读的当前修订：`content/catalog.json` 中 `currentRevisions` 指向的那个修订的 `.md` 和 `.json`。旧导读可以作为起点，但要按本文重写，不要只润色。
3. 从旧元数据里记下固定原文：`source.url` 和 `source.version`。新修订必须使用同一个固定版本，因为同一导读 ID 对应同一篇论文的同一版本。

### 第 1 步：取得固定原文

```text
mkdir -p .source-review/<id>
curl -sSL -o .source-review/<id>/source.pdf "<固定 PDF 地址>"
```

arXiv 论文还可以下载对应版本的 HTML（`https://arxiv.org/html/<编号>v<版本>`），用来查章节锚点。

把 PDF 转成文字，便于通读和检索：

```text
python3 -m venv .cache/pyreview && .cache/pyreview/bin/pip install pymupdf pillow   # 只需一次
.cache/pyreview/bin/python scripts/content/figure-tools.py text .source-review/<id>/source.pdf .source-review/<id>/source.txt
```

### 第 2 步：通读原文

**读正文全文。** 摘要、旧导读、二手资料都不能代替原文；附录按需要读。读的时候记下：

- 作者要解决的问题，以及他们认为已有方法卡在哪里；
- 核心方法的每一步：输入、处理、输出，以及关键公式和维度；
- 每张关键图、表在说什么，在 PDF 第几页；
- 主要实验的设置（数据、指标、对照）和结论；
- 作者自己承认的局限；
- 综述还要记下：分类框架，以及每个分支下点名的代表方法。

论文里第一次出现的缩写、方法名和术语，都要记下来，留到第 7 步处理。

### 第 3 步：确定核心，设计结构

**先回答一个问题：读者读这篇论文，最需要弄懂的是什么？** 例如 Transformer 的核心是图 1 的架构，其中最重要的是多头注意力；RAG 综述的核心是三种范式，以及各环节的代表方法。核心部分要占最多篇幅、讲得最细：必要时拆成两节，配原图、形状表和手算例子。其他部分按重要程度分配篇幅。

然后按论文类型设计章节。下面是起点，可以按论文实际调整：

**方法论文**（参考 Transformer r5）：

1. 开篇（无标题）：论文是什么、谁写的、解决什么问题、主要结果；为什么今天还值得读；全文核心是什么、导读按什么顺序读。
2. 背景：作者面对的问题，已有方法卡在哪里。这一节必须放在前面，让读者先知道作者为什么要这样做。
3. 任务定义：模型的输入、输出、要预测什么。
4. 全貌：对照论文的总体结构图或流程图，从头到尾走一遍。
5. 核心机制：一到三节，逐步拆开，配原图、公式、形状或步骤表，以及可以手算的小例子。
6. 其余组件。
7. 作者的论证：作者怎样说明这个设计合理，例如复杂度分析、理论推导。
8. 训练与实验设置。
9. 结果与消融：每组实验回答了什么问题。
10. 论文之后：后续影响（标明是编辑背景），推荐接着读什么。
11. 回到原文：哪几处值得亲自读，以及覆盖声明。

**综述**（参考 RAG 综述 r5）：

1. 开篇：领域要解决的问题，综述的贡献（它画了哪几张“地图”），这篇导读怎么读。
2. **按综述自己的章节顺序展开**，让读者能对照原文。每章对应一节或几节。
3. 综述的核心分类图要放在对应章节，并逐栏、逐块讲解。
4. 综述点名的代表方法，每个都按“要解决什么问题 → 具体怎么做 → 和相邻方法有何不同 → 原文或作者指出的局限”展开（见第四节第 7 条）。
5. 倒数第二节：方法地图，用表格把方法按环节整理；可以再加一张“从现象反查方法”的表。
6. 最后一节：原文入口与覆盖声明。

**评测或基准论文：** 背景 → 要测什么、为什么现有评测不够 → 任务与数据怎样构造（配原图或示例题）→ 指标与评分方法 → 主要结果与发现 → 局限与使用注意 → 回到原文。核心通常是“测量是否测到了它声称要测的能力”。

**系统或框架论文：** 背景 → 系统要解决的问题 → 架构总图 → 组件与数据流，用一个任务把流程走一遍 → 关键设计取舍 → 实验与案例 → 局限 → 回到原文。

单节篇幅一般在 1000–3500 字。核心节可以更长，但不要超过 8000 字（AI 问答按节读取导读）；更长时，就拆成“（上）”“（下）”两节。

### 第 4 步：写正文

按第四节的写作规范写。写完一节就对照原文核对这一节的数字、公式和说法，不要留到最后。

### 第 5 步：放原图

核心机制或核心分类所对应的原论文图，要放进正文对应的那一节，并围绕它展开讲解：先说怎么读这张图，再逐块解释。截图方法：

```text
.cache/pyreview/bin/python scripts/content/figure-tools.py locate .source-review/<id>/source.pdf
.cache/pyreview/bin/python scripts/content/figure-tools.py render .source-review/<id>/source.pdf <页码> .source-review/<id>/fig1.png <x0,y0,x1,y1> 4
.cache/pyreview/bin/python scripts/content/figure-tools.py webp .source-review/<id>/fig1.png content/guides/assets/<id>/figure-1-<简短英文名>.webp
```

`locate` 会列出每页的图片框、矢量图范围和图注位置。裁切范围通常从图片框四周各放宽 4–8 点，并且不要包含图注文字（图注由导读另写）。**裁切后必须打开 PNG 亲眼查看**，确认图完整、清晰、没有切掉边缘、没有多余空白。看不清就提高 zoom 重新截。

正文中的写法：

```markdown
![对图内容的完整文字描述，供看不到图的读者使用](assets/<id>/figure-1-xxx.webp "原论文图 1：图的中文标题与读法提示")
```

方括号里的替代文字要描述图的内容；引号里的标题会显示为图注。一篇导读放 2–5 张原图即可，只放讲解真正需要的图。

许可：仓库是私有的，原图带署名，供个人学术阅读使用。在 spec 的 `assets` 中如实记录许可依据：论文页面有明确复制许可时照录；只有 arXiv 默认许可时写“arXiv 默认非独占分发许可，未授予再发布权；仅在私有仓库中作个人学术阅读引用。”可在 `https://arxiv.org/abs/<编号>v<版本>` 页面的许可链接中查到。

### 第 6 步：写信息卡

见第六节。

### 第 7 步：术语

见第七节。

### 第 8 步：生成元数据并检查

```text
node scripts/content/new-revision.mjs .cache/guide-work/<id>/spec.json
node scripts/content/guide-work.mjs check <id>
```

**如果 `check` 报错指向的是其他导读的文件（例如另一篇的 `body hash mismatch`），说明别的作者正在修改那一篇。等几分钟再运行，绝对不要去改其他导读的文件。**

`check` 会在不改动共享文件的情况下，把新修订放进一份临时目录做完整校验：标题、章节、引用清单、资产哈希、信息卡章节名、术语表冲突、单节长度。报错就修，直到通过。正文改动后要重新生成元数据，因为正文哈希会变。

### 第 9 步：自查

按第十一节的自查清单逐条检查，并通读全文一遍：用读者的身份，从头读到尾。

### 第 10 步：写核对记录

见第十节。到这一步，作者的工作就完成了。合并（`node scripts/content/guide-work.mjs merge <id>`）和构建由整合者执行。

## 四、写作规范

这一节是质量的关键。下面每条都附了说明；“不好”的例子摘自被读者否定的旧稿，“好”的例子摘自样例。

### 1. 先找核心，篇幅给核心

不要平均分配篇幅。核心机制要讲到读者能“跟着算一遍”或“对着图讲一遍”：给出形状或步骤表，给出一个数值小到可以手算的例子，说明为什么要这样设计，再说明作者用什么实验支持这个设计。次要的训练细节、后续发展可以短。

### 2. 顺序：先建立认识，再展开细节

读者需要先知道“为什么”，再看“怎么做”。背景和问题放在机制前面；整体结构放在局部细节前面；概念要在第一次使用之前或使用的当下解释清楚。

> 不好：一开篇就让读者看图，图的讲解里已经在用“查询”“键”“值”，这三个概念到下一节才解释；作者为什么要去掉循环网络，到第 9 节才讲。
>
> 好：先讲 2017 年循环网络的瓶颈，再讲模型要预测什么，然后对照图 1 看全貌；讲图时只用读者已经知道的词，查询、键、值留到下一节，用“查资料”的类比引入。

### 3. 每节的写法

- **开头一两句交代这一节要回答什么问题，或承接上一节。** 例如：“上一节的注意力有一个特点：每个查询只算出一组权重……问题来了。”
- **按“概念 → 怎么做 → 例子 → 这意味着什么”展开。** 例子和机制要互相对得上。
- **一段只讲一件事。** 一段 3–6 句，句子完整，因果和转折清楚。
- **用自然的叙述把作者的推理串起来：** 作者注意到什么，于是怎么做，结果发现什么，作者自己怎么解释。区分“作者提出”“实验显示”“导读的解释”，但不必每句都贴标签，用“作者认为”“论文报告”“可以这样理解”自然带出即可。

### 4. 限定条件只说一次，说在结论处

审慎是对的，但不能让每段都以免责句收尾。规则是：一个结论的适用条件，在给出这个结论的地方说一次；同一条件不要反复说；全文的覆盖范围和未覆盖的内容，集中写在最后一节。

> 不好（每段都在防误读）：“这只比较给定取值下的混合步骤；换一套可学习的参数，单头也能算出许多其他表示。作者没有给头规定……”“看到一次位置敏感，还不能推出任何模型都按两端优先的方式读取。”“这组结果不能当作普遍适用的加长提示策略。”
>
> 好：把条件融进结论本身。“多头确实有帮助，但不是越多越好……这组实验同时改变了头数和每头的宽度，没有把两者的作用分开。”一个结论，一句条件，然后继续往下讲。

每段最多一处限定；只有当它会改变读者对结论的理解时才写。

**用数字自查。** `guide-work.mjs check` 会统计“不能、不等于、并不、不是、未必、不意味”每万字出现的次数。两篇样例约为 9；超过 14 时，检查会给出警告，说明正文读起来更像审稿意见。修改方法不是删词，而是改写：把否定句改成正面陈述（“X 不等于 Y”改为“X 说明的是……”），把条件并进结论，删去重复和节末的免责句。“不是 A，而是 B”这类用来澄清概念的句子可以保留。

**目标不是归零。** 合适的范围大约是每万字 5–12 处；低于 4 往往说明把必要的条件也删掉了。下面这些条件会改变读者对结论的理解，必须保留，并且说清楚它影响什么：样本量很小、只在开发集或特定数据集上测试、比较的双方条件不同（模型、数据、预算）、作者的解释没有经过实验验证、结果来自人工指定的教学例子。

> 不好（删掉了必要条件）：“每类样本各有 50 条，这些比例帮助作者理解不同的错误类型。”
>
> 好：“由于每类只抽了 50 条，这些比例适合用来理解错误有哪些类型，不宜当作各类错误的真实发生率。”

**同一个保留意见只说一次。** 如果上一段已经说明“这是作者的解释，不是证明”，下一段就不要换个说法再说一遍。原表中与本节论证无关的对照行（例如另一条技术路线的系统），不必专门写一段来说明“它不可比”，直接不摘录即可。

**特别注意节末。** 不要在一节的最后再补一句“这不能证明……”“还需要一起考虑……”。节末应该落在这一节得出的认识上。

> 不好（节末免责）：“图 3 没有证明某个规模是通用门槛；它说明在该实验中，评估一种交互格式不能只看一个模型的一次提示结果。”
>
> 好（节末落在认识上）：“这组实验说明，ReAct 既可以作为提示方法用于冻结的大模型，也可以把同样格式的轨迹用来微调较小的模型；评价一种交互格式时，模型规模和适配方式都会改变结论。”“不等于”“不能说明”“并不表示”在全文中应该少见。

### 5. 讲解，不要发指令

导读是讲给读者听的，不是操作手册。少用“看看……”“试试……”“遮住……再……”“回头检查……”这类祈使句。需要读者动手的地方（例如手算、对照原图）集中在一两处，说清楚为什么值得这样做。

> 不好：“暂时遮住输出端，只看右侧中间那三条线。如果你能指出哪一条……就可以打开图 2。”
>
> 好：“再看右侧。‘〈起始〉 他们 来到了’从右下角进入……然后它进入中间的交叉注意力，带着这份信息去编码器的输出里查找。”

### 6. 例子：有用的地方才用，用了就标明

- **优先使用论文自己的例子。** 论文正文或图里通常已有一个完整的示例（ReAct 图 1 的 Apple Remote 问答、Transformer 的翻译任务），沿着它讲最自然，也最可信。不要借用其他导读的例子（例如“青榆站”只属于 RAG 综述）。论文没有合适的例子时，再自编一个。
- 一篇导读最好有一个贯穿的教学例子（Transformer 用“river bank → 河岸”的翻译，RAG 综述用虚构的“青榆站”档案问答），在核心环节反复使用，帮助读者看清机制。
- **例子是为讲清方法服务的，不能喧宾夺主。** 先把方法本身讲清楚，再用例子说明它在具体情境中的表现。不要每介绍一个方法都套一遍例子；综述里，例子只用在能区分不同环节、不同失败的地方。
- 手算例子要小到能用纸笔算完，数值可以人为指定，算完要能说明一个关键性质（例如“单头一组权重做不到两头能做的事”）。
- 自编的例子在首次出现时说明“这是导读自编的教学例子”，文末覆盖声明里再列一次。不要让读者误以为是论文的实验。

### 7. 综述里的代表方法：四要素

综述点名的方法，读者最需要知道的是四件事：

1. **要解决什么问题**：它针对的是哪种失败或不足；
2. **具体怎么做**：两三句话讲清机制，不要只写一个名词；
3. **和相邻方法的区别**：例如 HyDE 和 RRR 都改查询，区别在于前者生成整段假设文档，后者训练改写器改写一句查询；
4. **局限或代价**：取自原论文或综述的说法；没有就不写，不要编。

方法的做法以综述的描述为准，并到原论文的 arXiv 摘要页核对（`https://export.arxiv.org/api/query?id_list=<编号>` 可以批量取摘要）。综述的说法与原论文不一致时，以原论文为准，并在正文中说明。

### 8. 公式、表格与图

- **公式**：写出论文的关键公式（KaTeX 语法），紧接着用文字解释每个符号和它在做什么。导读为了说明而自己写的公式要注明“这是导读的记号”。
- **表格**：用于形状变化、方法对比、实验结果摘录、通路对比。实验表只摘录与论证相关的行，并在表前说明测试集、指标方向和条件。表格前后要有文字解释“从表中读出了什么”。
- **原图**：图放在讲它的那一节开头附近。先说怎么读（从哪里看起、方向、颜色），再逐块讲解，最后说明这张图在全文论证中的作用。

### 9. 出处链接

关键事实、数字、图表后面附原文链接，标签写清位置，例如 `[§3.2.1、图 2 与式 1，PDF 第4页](<固定 PDF 地址>#page=4)`，或者 arXiv HTML 的章节锚点。同一个地址的不同标签都可以用，脚本会自动建立引用清单。站内导读链接一律写固定修订：`/read/<id>/<修订号>#<单元 id>`。

### 10. 语言细节

- 中文为主，术语第一次出现时给英文原名或缩写，例如“交叉注意力”“检索增强生成（RAG）”。缩写会由术语表自动加虚线，不必在正文里解释全称来历，但正文要让读者不点开也能读下去。
- 用完整的句子和自然段，不要把讲解写成清单。清单只用于并列的步骤、类别或检查项。
- 少用“值得注意的是”“需要指出的是”“总而言之”这类套话。
- 不夸大，不贬低。“作者认为”“论文报告”“原论文的实验显示”要用准。
- 一句话里不要塞三个以上的从句或括号。

## 五、篇幅参考

| 部分 | 参考篇幅 |
| --- | --- |
| 全文 | 方法论文 15000–22000 字，综述 18000–26000 字 |
| 开篇 | 600–1200 字 |
| 核心机制（合计） | 全文的 30%–40% |
| 单节 | 一般 1000–3500 字，最多 8000 字 |
| 信息卡三部分 | 概述 3–4 段，为什么值得读 2–3 段，阅读建议 2–3 段 |

篇幅是参考，不是目标。判断标准是读者能否读懂、能否看到作者的思考；不能为了凑字数重复。

## 六、信息卡

信息卡只有文字，不放图。`brief.json` 格式：

```json
{
  "guideId": "<id>",
  "guideRevision": <N>,
  "overview": "第一段……\n\n第二段……\n\n第三段……",
  "value": "……\n\n……",
  "advice": "……\n\n……",
  "chapterLabels": { "<单元 id>": "8–12 字的短章节名", "...": "..." },
  "sourceUpdatedAt": null,
  "sourceRecordUrl": null
}
```

- `chapterLabels` 必须覆盖所有带标题的单元（开篇除外），id 与正文一致。
- `sourceUpdatedAt` 和 `sourceRecordUrl` 照抄该导读上一修订的信息卡。
- 段落之间用一个空行（`\n\n`）分隔。

三部分各回答一个问题：

- **概述**：这篇论文讲了什么。依次写清：问题背景、作者做了什么（核心方法或分类框架，用读者能懂的话讲到具体机制）、主要证据和结果（带关键数字）、局限和在领域中的位置。
- **为什么值得读**：读完能获得什么。写具体的能力，例如“能看懂一张结构图、说出每个模块的输入来自哪里”，或“能判断一篇新论文改的是哪一环”；也可以写这篇论文作为“读论文范例”的价值。不要写“具有重要意义”这类空话。
- **阅读建议**：需要什么先修知识（正文会解释哪些）；建议的阅读顺序，以及哪几节是重点、值得慢读；常见误读；读完后是否值得读原文、读哪里。

信息卡写的是这篇论文，不是导读本身；不要写“本导读第几节”，可以写“正文中的某某部分”。

## 七、术语表

正文中第一次出现的缩写和方法名，会根据 `content/glossary.json` 自动加虚线，点开显示卡片。写完正文后：

1. 列出正文中出现的缩写、方法名和重要术语。
2. 在 `content/glossary.json` 中查找，包括 `aliases`。已有的就不用管。
3. 缺少的写进 `.cache/guide-work/<id>/glossary.json`：

```json
{ "entries": [
  { "id": "sft", "term": "SFT", "aliases": ["SFT", "监督微调"],
    "full": "Supervised Fine-Tuning", "zh": "监督微调", "field": "大模型训练 · 微调",
    "explain": "两到四句通俗解释：它是什么、怎么做。",
    "builds": "可选：改进自什么、和谁相关、谁提出。",
    "guide": "/read/instructgpt/2#u03",
    "source": { "label": "arXiv 原文", "url": "https://arxiv.org/abs/2203.02155" } }
] }
```

- `id`：小写字母、数字和连字符，全局唯一。
- `aliases`：正文里实际出现的写法，大小写敏感。英文别名按整词匹配。不要用太常见或有歧义的词作别名，否则会到处加虚线，甚至加错卡片：例如“量化”在评测文章里常指“可量化”，应写成“模型量化”；英文的 decode、Flooding 这类普通词也不要单独作别名。别名不能和已有条目重复。
- `field`：“领域 · 类别”。
- `guide`：本库中专门讲它的导读，写固定修订；没有就省略。
- `source`：原始论文，必须核对过编号对应的标题（用 arXiv API）；不确定就省略。
- 解释要让新手看懂，且准确；通用概念的解释属于编辑背景知识。

## 八、原图与许可

见第三节第 5 步。补充两点：

- 每张图在 spec 的 `assets` 中都要有 `alt`、`origin`（原图所在页面的固定地址，例如 PDF 加 `#page=N`）和 `rights`（来源和许可依据）。
- 不要放与讲解无关的图；不要把表格截成图，表格用 Markdown 重写需要的行。

## 九、spec.json 格式

```json
{
  "base": "<id>.json 或 <id>.r<上一修订>.json",
  "revision": N,
  "bodyFile": "<id>.r<N>.md",
  "out": "<id>.r<N>.json",
  "unitIds": ["<开篇单元 id>", "<第 1 个 ## 节的 id>", "..."],
  "citationInfo": [ { "prefix": "https://arxiv.org/abs/2312.05934", "role": "background", "sourceVersion": "arXiv 摘要页（综述引用文献 [28]）" } ],
  "assets": { "assets/<id>/figure-1-xxx.webp": { "alt": "……", "origin": "……#page=3", "rights": "……" } },
  "top": { "purpose": "一句话说明这篇导读帮读者弄懂什么" },
  "coverage": { "scope": "mainline", "basis": "fulltext", "sections": ["……"], "figuresViewed": ["Figure 1 — PDF p3 (reproduced)"], "limitations": ["……"], "reviewBasis": "……" },
  "orientation": { "summary": "……", "value": "……", "readingTargets": [ { "unitId": "…", "purpose": "读完本节能分辨或解释什么", "concepts": ["…"], "limit": "结论不能推广到哪里" } ] }
}
```

- `base`：上一修订的元数据文件。论文身份、来源、书目、主题等字段从它继承，不需要重写。
- `unitIds`：第一个是开篇（无标题部分）的 id，之后与正文 `##` 标题一一对应。语义延续的单元沿用旧 id，新内容用新的有意义的 id，例如 `background`、`architecture`。
- `citationInfo`：正文中引用的、不属于固定原文的链接（例如被引论文的摘要页），用前缀标为 `background` 并写明来源说明。固定原文的链接默认为 `primary`。
- `coverage.limitations`：如实写清没覆盖的部分、教学例子的性质、没有复现实验等。
- `orientation.readingTargets`：给核心章节写，`unitId` 必须存在。

## 十、核对记录

`docs/research/<id>-r<N>-review.md` 写清以下几项：

- 固定原文与版本，实际读了哪些页、哪些章节；
- 查看过哪些原图、表格（裁切后亲眼确认过的原图要单独写明）；
- 每个关键数字和机制说法对照的原文位置。可以用表格，列出“导读说法 | 原文位置 | 核对结果”，覆盖核心章节和全部实验数字；
- 发现的原文问题或与旧导读的出入；
- 没有核对或无法核对的内容。

不要把审稿式的保留意见搬进正文；它们属于这份记录。

## 十一、自查清单（作者交付前逐条检查）

**内容**
- [ ] 读完正文全文，所有数字、公式、图表说法都对照过固定原文。
- [ ] 能用一句话说出这篇导读的核心，并且核心部分篇幅最多、讲得最细。
- [ ] 核心机制有原图、步骤或形状表，以及可以手算的小例子（适用时）。
- [ ] 综述的每个代表方法都讲到四要素，且做法与原论文摘要一致。
- [ ] 自编例子标明了身份，后续影响标明是编辑背景。

**结构与语言**
- [ ] 背景和问题在机制之前；每个概念在使用之前或使用时就解释了。
- [ ] 每节开头交代这一节回答什么问题，段落之间有承接。
- [ ] 限定条件只在结论处说一次；“不等于 / 不能 / 并不”没有成串出现。
- [ ] 没有成段的祈使句和操作指令。
- [ ] 读起来像一位有经验的研究者在讲这篇论文，而不是罗列知识点或写审稿意见。

**文件**
- [ ] `node scripts/content/guide-work.mjs check <id>` 通过。
- [ ] 每张原图都亲眼看过裁切结果。
- [ ] 信息卡三部分都写足，没有图。
- [ ] 新术语已写入 glossary 片段，编号核对过。
- [ ] 核对记录已写。

## 十二、审查（整合者或审查者使用）

审查者先读这篇论文的关键页，再从读者视角通读导读全文，重点看：

1. **能不能读懂：** 一个没读过原文的研究生，读完能否对着关键图讲清核心机制？
2. **核心够不够细：** 核心部分是否有步骤、例子和设计理由，而不只是名词？
3. **语言：** 是否连贯、自然；是否有免责句堆积、指令式写法、概念先用后讲、例子喧宾夺主？
4. **准确：** 抽查核心章节和实验部分的数字、公式、方法描述，对照原文。
5. **信息卡：** 三部分是否具体，有没有空话。

发现的问题直接修改。如果同类问题反复出现，说明本文写得不够清楚，要把对应规则补进本文，并附上“不好 / 好”的例子。
