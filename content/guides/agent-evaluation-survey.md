# Agent 评测综述：把能力、行动过程与任务结果连接起来

当模型进入可以查询信息、调用工具并改变环境的系统，评价对象随之改变。一段回答的质量仍然重要，但它不能独自说明系统有没有完成目标、是否遵守限制、付出了多少成本。《Survey on Evaluation of LLM-based Agents》从能力、应用、通用 Agent 和评测框架四个角度组织这个问题，适合用来建立后续选读具体基准的地图。[原文 v1，§1 与图1，PDF 第1–2页](https://arxiv.org/pdf/2503.16416v1#page=2)

本文依据 [2025 年 3 月的 arXiv v1](https://arxiv.org/pdf/2503.16416v1)，围绕如何组织评价证据作主线讲解。该文后来发表于 Findings of ACL 2026，正式版增加了内容；本文不把两版的章节、分类和结论混在一起。原文的未来方向是当时的判断，尚不足以证明今天某个方向仍是研究空白。

## 先明确被测的是哪一套系统

模型提供生成与推理能力，Agent 则通过上下文、记忆、工具和控制流程把多次模型调用连接起来。一次失败可能来自模型判断、工具描述、信息传递、环境反馈或流程限制。因此，报告一个 Agent 分数时，需要能说明模型和系统配置，否则无法判断改变发生在哪里。[§1 与范围说明，PDF 第1–3页](https://arxiv.org/pdf/2503.16416v1#page=1)

可以用一个教学例子理解这种差别：系统被要求核实一条记录后提交更新。模型可能正确解释更新规则，却选择了错误记录；也可能选择正确，但工具参数格式不合法；还可能工具执行成功，却没有告知用户必要信息。三种情况下最终体验都不好，改进方向却不同。评价既要保留最终结果，也要能回到导致结果的观察与行动。

这不意味着必须把全部内部推理文字当作真实认知过程。可检查的对象首先是输入、工具调用、返回值、状态变化和最终输出。轨迹中的自然语言理由可以帮助理解，但它本身仍是系统输出，不能单靠自述认定错误原因。

## 能力测试让问题变小，端到端测试检查能力能否组合

原文能力部分讨论规划与多步推理、函数调用与工具使用、自我反思、记忆四类。规划关注目标分解和状态推进；工具使用涉及选工具、填参数、理解返回并继续行动；反思关注收到反馈后的修正；记忆则让过去的信息在需要时可用。这些能力在一条任务轨迹中往往交叉出现，不是互相独立的模块得分。[§2，PDF 第3–6页](https://arxiv.org/pdf/2503.16416v1#page=3)

局部测试可以把条件固定得更清楚。例如只给定一段工具描述与请求，检查函数选择和参数，可以发现接口理解问题；但把正确参数放回完整任务后，Agent 还需要知道何时调用、是否缺少确认、之后怎样判断返回。因此，局部能力高分应当作为机制证据之一，不能替代真实任务评价。

反思和记忆尤其需要注意额外信息与预算。若改进方法比基线多看了反馈、多运行了几次，结果提高可能同时包含纠错机会和更多计算的作用。比较前应说明反馈由谁提供、哪些信息在运行时可见，以及重试和调用预算。这里是对综述能力分类的实验设计解释；不能从分类本身推导某种记忆或反思实现一定有效。

## 一项应用基准同时定义任务、环境与指标

原文把应用基准拆成任务数据、运行环境和评价指标。任务说明要达到什么目标，环境规定能观察和能操作什么，指标说明怎样判定结果；三者缺一就难以解释测到了什么。网页、软件工程、科学任务和对话服务的评价差异，正来自这些定义的变化。[§3，PDF 第6–9页](https://arxiv.org/pdf/2503.16416v1#page=6)

网页任务可能检查操作路径及最终页面或后台状态；软件工程任务往往需要在给定代码环境中运行验证；科学任务涉及信息整合、实验设计或可执行计算；服务对话则要同时处理用户信息、领域规则与工具动作。不能仅因为它们都使用 LLM，就把各自的分数按同一含义理解。特别是“单步预测正确”和“让整个环境到达目标状态”是不同评价对象。

阅读这份综述时，应把代表基准当作查阅入口。本文没有逐一重审每个被引系统，尤其不沿用其中所有关于实时网页、离线轨迹或框架功能的简写作为实施事实。准备采用某个环境时，仍需核对其原论文、数据划分和运行版本，明确是否真正执行动作、是否使用模拟用户，以及何种结果可以被验证。

## 结果、步骤和完整轨迹回答不同问题

结果评价问任务是否完成；步骤评价问某次行动是否合适；轨迹评价则检查行动之间的顺序、依赖、重复与恢复。原文在框架部分明确讨论这几种粒度，以及模型裁判与参考路径的可靠性问题。[§5，PDF 第10–11页](https://arxiv.org/pdf/2503.16416v1#page=10)

只看结果容易漏掉过程风险。例如先做了未经确认的操作再恢复，最终状态可能正确，但过程仍违反规则。只看步骤又可能鼓励局部看似合理的动作，而忽略系统迟迟不能完成目标。更有用的组织方式，是把终点判据和关键过程约束并列：前者说明是否达成目标，后者指出哪些错误即使不改变终点也需要记录。

参考轨迹也不是唯一正确答案。两个系统可能以不同顺序查询同样必要的信息，最后都得到正确结果；若逐条强制匹配一条标准轨迹，就可能把有效策略判错。反过来，仅用一个宽泛的模型裁判打总分，又可能缺少稳定、可定位的错误依据。如何兼顾多种有效解和诊断粒度，是评测设计需要说明的取舍，不是增加更多指标就自动解决的问题。

| 观察层次 | 有助于回答 | 仍需补充的证据 |
| --- | --- | --- |
| 最终结果 | 目标是否完成、必要输出是否提供 | 过程是否合规，是否存在未观测副作用 |
| 单步行动 | 工具、参数和当前判断是否合适 | 动作在完整任务中的作用 |
| 完整轨迹 | 怎样推进、在哪里循环或恢复 | 参考路径是否容纳其他有效方案 |
| 成本与重复运行 | 相同约束下是否稳定且可承担 | 任务分布、预算口径和评价版本 |

这张表是教学整理，不是论文原表或新实验结果。

## 通用能力需要跨任务证据，也要保留各任务的差异

通用 Agent 基准把多个任务或环境放在一起，试图观察系统能否迁移到不同条件。原文在这一部分介绍 AgentBench 等交互集合，以及计算机操作和数字工作环境中的评测。其价值在于暴露能力分布，而不只是增加一个总分。[§4，PDF 第9页](https://arxiv.org/pdf/2503.16416v1#page=9)

跨任务汇总时，样本数和权重都会影响总体结论。简单按任务数平均，会让样本多的领域占更大比重；先按领域平均，则表达领域同等重要的选择。两种方式都需要说明目的。下一篇 AgentBench 可用来观察分领域指标怎样被归一化，而 τ-bench 则展示重复成功和至少一次成功为什么应分开。

对于多 Agent 系统，还需要明确被测对象是整个团队还是单个角色。团队最终成功不能直接证明每条消息都必要，也不能直接区分协作收益和更多模型调用的作用。这里是面向通信研究的编辑联系；本综述 v1 没有全面覆盖多 Agent、具身和游戏评价，不足以单独制定完整的多 Agent 通信实验协议。

## 成本、裁判与环境都属于评价条件

原文讨论的不足包括细粒度诊断、成本效率、自动评价扩展和安全合规。如果系统可以无限重试，高成功率就可能伴随无法接受的时间和调用代价；如果裁判与被测系统具有相似偏差，自动化规模扩大也未必增加可信度。运行环境变化同样可能改变结果，而不是只改变操作难度。[§6，PDF 第11–12页](https://arxiv.org/pdf/2503.16416v1#page=11)

准备比较方案时，可先固定任务、环境快照和预算，再保存各次运行的实际成本、终止原因与结果。若需要更新测试集，应保留版本与变化理由，使前后结果能够被解释。这个建议的目的不是把每次尝试变成大型评测工程，而是让关键结论有明确边界：究竟是在相同资源下更可靠，还是用了额外信息或额外尝试。

## 怎样接着阅读并形成可研究的问题

先用图1确认能力与应用的关系，再读 §3 的任务—环境—指标定义，以及 §5 对步骤和轨迹的讨论。随后读 HELM，补齐场景与适配意识；读 AgentBench，观察跨环境指标与失败归类；读 τ-bench，检查终点规则、政策过程和重复运行可靠性之间的缺口。阅读顺序是编辑建议，不意味着这些论文已经解决所有评价问题。[图1与阅读地图，PDF 第2页](https://arxiv.org/pdf/2503.16416v1#page=2)

形成方向时，可以先提出能被证据区分的问题，例如“终点成功的轨迹中有多少违反关键过程约束”或“多次运行的不稳定主要发生在哪一步”。这些是待检验的问题，不是本文认证的创新点。综述提供了整理证据的坐标，是否值得深入仍需查近邻工作、实际任务和可取得的数据。
