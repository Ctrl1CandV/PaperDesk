# ReAct：让推理、行动与环境反馈形成循环

ReAct 研究的不是让模型多写几步解释，而是怎样让这些解释参与接下来的行动，并让行动得到的信息改变后续判断。对一项需要查资料或操作环境的任务，答案并不都在模型最初看到的输入里。系统要决定还缺什么信息、采取哪一步、如何理解返回结果，再决定继续还是结束。这使 ReAct 成为从 Agent 架构综述进入具体方法的一篇合适论文。[原论文 v3，§1–2，PDF 第1–4页](https://arxiv.org/pdf/2210.03629v3)

本文依据 arXiv v3，即作者注明的 ICLR 2023 camera-ready 修正版，解释方法、主要对照实验和失败条件。它不是当前模型能力的排名，也不是对所有工具型 Agent 的完整综述。理解它之后，值得保留的判断方式是：每一步文字究竟只是模型的推断，还是已经从环境获得了证据？

## 从生成文字到选择行动，中间需要明确的接口

普通语言模型根据上下文生成下一个词；Agent 系统还要把一部分生成内容解释为可执行操作。论文将已有观察和行动组成上下文 $c_t$，用策略 $\pi(a_t\mid c_t)$ 表示下一步动作的选择。这里的“策略”是根据当前信息决定做什么的规则，并不意味着必须通过强化学习训练。[§2，PDF 第3页](https://arxiv.org/pdf/2210.03629v3#page=3)

ReAct 把可选择的内容扩展为 $\hat{\mathcal A}=\mathcal A\cup\mathcal L$：$\mathcal A$ 是环境允许的动作，$\mathcal L$ 是自然语言思考。两者的区别在于作用对象。执行搜索可能带回一段网页；生成“先确认实体，再比较日期”只会更新模型随后可见的上下文，不会凭空产生新的外部事实。模型可以通过这种文字整理目标、提取线索和修正计划，执行器则负责把动作送到环境并返回观察。

这也是阅读轨迹时应保留的三种身份：Thought 是模型写出的判断，Action 是提交的操作，Observation 是工具或环境的返回。后者也需要检查来源和内容，但不能把模型自己写出的一个“观察”当成工具执行的证据。这个区分既有助于理解论文，也有助于分析实际系统为什么失败。

知识问答实验把接口限制为三种操作。`search[entity]` 找实体页面，存在时返回开头五句，不存在时给相近实体；`lookup[string]` 在当前页面继续找包含该词的句子；`finish[answer]` 提交答案并结束。因此，ReAct 使用的是特定检索接口，并非任意浏览器能力。检索范围和返回粒度会直接限制模型能够取得的证据。[§3.1，PDF 第4页](https://arxiv.org/pdf/2210.03629v3#page=4)

## 推理与行动的联系，在观察之后才真正成立

核心循环可以理解为：先根据任务和已有材料提出一个局部目标，采取能够减少当前不确定性的行动，再检查返回信息是否真的回答了问题。新信息支持原计划时继续，不支持时就修改查询或步骤。原文图1将这种轨迹与只回答、只推理、只行动的方式放在一起，展示了推理如何决定搜索对象，也展示了搜索失败如何改变后续推理。[图1及说明，PDF 第2页](https://arxiv.org/pdf/2210.03629v3#page=2)

以下是本文自拟的教学情境，不是论文实验：要确认两种软件功能是否兼容，先查第一个功能的版本要求，再查第二个功能的依赖。如果第一次返回的只是产品简介，就不能直接作“兼容”的结论；下一步应寻找版本文档。把已有推断写得更长，不会替代这次缺失的检查。这里重要的是观察能否改变行动，而不是轨迹是否机械地重复三种标签。

```mermaid
flowchart LR
  A[任务与已有上下文] --> B[整理目标与缺失信息]
  B --> C[选择并执行环境动作]
  C --> D[取得外部观察]
  D --> E[核对证据并更新上下文]
  E --> B
  E --> F[条件满足时结束]
```

教学示意：整理与执行的循环，非原论文图。文字流程与图一致：任务和已有上下文进入局部计划；执行产生新观察；核对之后继续或结束。它并不表示每个行动前都必须生成长篇推理。

原论文正是根据任务改变思考密度：问答中的推理与动作较密集地交替；较长的交互任务则只在分解目标、完成子目标或调整计划等位置插入思考。主要提示实验使用冻结的 PaLM-540B 和少量人工编写的完整轨迹示范。示范包含动作与真实观察，不只是“请逐步思考”一句指令。论文另有微调实验，不能把整篇工作概括成只研究提示、不涉及训练。[§2–3.2，PDF 第3–5页](https://arxiv.org/pdf/2210.03629v3#page=3)

## 问答实验说明了收益，也暴露了检索的代价

HotpotQA 需要跨多个段落回答问题，FEVER 要判断一个陈述是否被支持、被反驳，或证据不足。论文采用仅给问题或陈述、不预先提供支持段落的设定。HotpotQA 使用六个示范，FEVER 使用三个；外部信息需通过前述接口取得。因此比较的对象是这种输入、模型和工具条件下的解题方式。[§3.1–3.2，PDF 第4页](https://arxiv.org/pdf/2210.03629v3#page=4)

下表选取原表1的三个直接对照。模型均为 PaLM-540B；HotpotQA 指标是答案精确匹配率 EM，FEVER 是分类准确率 Acc，单位为百分比。它们不是推理步骤的正确率。

| 提示方式 | HotpotQA EM | FEVER Acc | 对照时保留的信息 |
|---|---:|---:|---|
| CoT | 29.4 | 56.3 | 推理文字，无外部行动与观察 |
| Act | 25.7 | 58.9 | 行动与观察，无显式思考 |
| ReAct | 27.4 | 60.9 | 推理、行动与观察共同参与 |

[表1与对照设置，PDF 第5页](https://arxiv.org/pdf/2210.03629v3#page=5)

ReAct 在这两项任务上都超过 Act，支持“观察本身不足以替代组织信息的推理”。但它在 HotpotQA 上低于 CoT，所以不能从论文抽出“接上工具必然更强”的结论。工具带来事实，也带来查询失败、信息不全和错误恢复的负担。

作者对 HotpotQA 的成功与失败轨迹作了抽样人工分析。其观察包括：CoT 容易生成错误事实，ReAct 则会因无效搜索、重复步骤或推理失误失败。这个分析只针对所抽样本；不能把表中某类错误的零出现，解释为该方法保证消除幻觉。[§3.3、表2，PDF 第6页](https://arxiv.org/pdf/2210.03629v3#page=6)

论文还结合 ReAct 与 CoT 自一致性：一条路径是在限定步数内不能完成时退回多次推理投票，另一条是在投票不集中时转向检索。CoT-SC 基线采样21条轨迹；混合方案的收益也包含额外采样或切换策略的作用。比较它们时，既要看正确率，也要看模型调用、搜索次数和终止条件，不能把不同计算预算下的成绩当成同一次生成的对比。[§3.2、表1、图2，PDF 第5页](https://arxiv.org/pdf/2210.03629v3#page=5)

## 长任务中的收益来自子目标管理，而不只是查到事实

在 ALFWorld 的文字家庭环境中，任务可能要求找到物体、处理物体并把它放到指定位置。观察不完整，动作也有先后条件。思考轨迹可以用来维护“已经拿到什么、哪一步完成、还缺什么”，从而减少在错误位置重复执行无效操作。这里的语言是工作信息，不是事后给成功结果配一段解释。[§4，PDF 第7页](https://arxiv.org/pdf/2210.03629v3#page=7)

实验覆盖134个未见评测游戏，每种任务从三条标注轨迹中取两条排列，构成六组提示。原表3报告 ReAct 六组的总体平均成功率为57%，最好一组为71%；Act 最好一组为45%。71%不是对任意提示都成立的平均水平。作者也提供移除思考的控制对照，用于检查同样的轨迹示范中，显式推理是否增加帮助。[表3及提示条件，PDF 第7–8页](https://arxiv.org/pdf/2210.03629v3#page=8)

WebShop 则要求在一个购物研究环境中，根据属性约束搜索、选择商品和选项。它同时报告平均属性匹配分数与完整任务成功率，两者不能混用。原表4在500条测试指令上给出的成功率为 ReAct 40.0%、Act 30.1%，专家人类为59.6%。结果表明所用提示下加入推理有帮助，也说明距离可靠满足全部要求仍有差距。这是研究基准中的交互，不是实际付款购买；实验也未证明它能适应任意真实网站。[§4、表4及伦理说明，PDF 第8–10页](https://arxiv.org/pdf/2210.03629v3#page=8)

## 把可检查的轨迹与可靠的推理区分开

ReAct 的工程价值之一，是把计划、动作和返回信息放到可检查的过程中。失败时可以追问：是问题拆错、检索参数不合适、工具没有返回关键事实，还是拿到事实后综合错了？这种诊断比只看最终答案丰富。但可读的推理文字并不自动忠实描述模型内部的因果过程，轨迹中合理的语句也不构成结果正确的证明。这是读者解释该方法时应保留的边界。

论文指出，复杂动作空间可能需要更多示范，而示范会受到输入长度限制。模型规模也影响是否能仅凭少量轨迹掌握格式：其 HotpotQA 实验中，较小 PaLM 模型直接使用 ReAct 提示的表现较弱，利用正确轨迹微调后才明显改善。由此应分开考察“循环结构是否有用”和“当前模型是否会稳定执行这个结构”。[§3.3、图3，PDF 第6–7页](https://arxiv.org/pdf/2210.03629v3#page=7)

如果把思路用于新任务，至少需要说明动作集合、观察来源、允许的重试、成功判据和资源预算。只写一个循环而不规定这些条件，很难判断改进来自更好的推理，还是更多机会或更强工具。这里提出的是从论文延伸的比较问题，不是已经得到验证的新研究方向。要进一步学习如何分解评价条件，可接着看本库的 [HELM 阅读](helm.md)；需要放回整体架构时，可返回 [Agent 综述](agent-survey.md)。

## 带着明确目的回到原文

先看图1及§2，逐一分清哪些文字由模型产生，哪些来自环境，以及一次搜索失败怎样改变下一步。这比只记住 Thought–Action–Observation 三个标签更重要。[图1，PDF 第2页](https://arxiv.org/pdf/2210.03629v3#page=2)

再把表1与§3.3一起读：找出 ReAct 未超过 CoT 的情形，理解为什么引入检索还需要有效的查询与失败恢复。阅读图2时同时查看采样次数，避免只比较最高的曲线终点。[表1、图2及分析，PDF 第5–6页](https://arxiv.org/pdf/2210.03629v3#page=5)

如果关注交互应用，阅读§4的设置与表3、表4，尤其区别平均提示结果、最好提示结果、属性分数和成功率。本文覆盖研究主线与这些关键证据，未逐条讲解全部附录轨迹，未复现实验，也没有验证开放环境中的长期可靠性。[§4，PDF 第7–8页](https://arxiv.org/pdf/2210.03629v3#page=7)
